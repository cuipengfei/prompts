# Glossary — Building Evolutionary Architectures

**Adaptation** — 让某个东西先能工作，不强调优雅性；与 evolution 相对，后者是被明确引导的变更 (Ch 1)
**Architectural Dimension** — 在演化过程中必须被保留的架构视角：technical、data、security、operational (Ch 1)
**Architectural Fitness Function** — 对某些架构特征进行客观完整性评估的机制 (Ch 2)
**Architectural Quantum** — 具备高功能内聚、且可独立部署的最小组件单元，包含其所有依赖元素 (Ch 4)
**Atomic Fitness Function** — 在单一上下文中运行，只检验架构的一个方面 (Ch 2)
**Bit Rot** — 当开发者绕过架构时，架构特征会逐步被侵蚀 (Ch 1)
**Bounded Context** — DDD 概念：某个领域相关的一切在内部可见，但对其他 context 保持不透明 (Ch 4)
**Business Capability** — 以领域为中心的组织单元；团队应围绕它组织，而不是围绕技术职能组织 (Ch 8)
**Component** — modules 的物理打包形式 (Ch 4)
**Consumer-Driven Contracts** — consumer 为自己需要的 provider 行为编写测试；provider 负责持续让这些测试通过 (Ch 8)
**Continuous Deployment** — pipeline 成功后自动部署到 production (Ch 3)
**Cycle Time** — 一个工作单元从启动到完成的耗时；与演化速度成反比 (Ch 3, 7)
**Deployment Pipeline** — 用于验证系统是否已具备生产就绪性的多阶段构建机制 (Ch 3)
**Dynamic Equilibrium** — 软件开发生态系统中不断变化的平衡状态 (Ch 1)
**Expand/Contract Pattern** — 数据库重构模式：先加入新状态 → 通过 triggers 同时维护新旧两套状态 → 等 consumer 迁移后移除旧状态 (Ch 5)
**Feature Toggles** — 在 production 中隐藏新功能的可配置开关；用于解耦 deployment 与 release (Ch 3)
**Fitness Function Review** — 定期会议（至少每年一次），用于更新 fitness functions (Ch 2)
**Fluid Dependency** — 通过 pipeline 自动升级到下一版本；若升级失败，则转为 guarded dependency (Ch 6)
**Goldilocks Governance** — 通过 3 套标准化技术栈（simple/intermediate/complex）实现恰到好处的技术选型 (Ch 7)
**Holistic Fitness Function** — 在共享上下文中运行，同时检验多个架构方面的组合效果 (Ch 2)
**Hypothesis-Driven Development** — 将功能变更表述为 hypothesis，并通过 A/B experiments 验证 (Ch 3)
**Immutable Infrastructure** — 系统完全以程序方式定义；bootstrap 之后不再允许手工变更 (Ch 6)
**Incremental Change** — 团队以小步方式构建和部署软件的做法 (Ch 1, 3)
**Inverse Conway Maneuver** — 按目标架构来设计团队结构 (Ch 1)
**Last 10% Trap** — 工具往往能快速解决前 80%，接下来的 10% 极难，最后 10% 几乎无法完成 (Ch 7)
**Module** — 相关代码的逻辑分组 (Ch 4)
**Parallel Change** — 用于安全实施向后不兼容接口变更的通用模式 (Ch 5)
**PenultimateWidgets** — 书中贯穿使用的示例公司，用来说明各类概念 (Ch 1)
**Primordial Abstraction Ooze** — 底层一个失效的 abstraction 会一路渗透各层并引发混乱 (Ch 7)
**Refactoring** — 在不改变外部行为的前提下重组代码 (Ch 6)
**Restructuring** — 同时对结构与行为进行实质性修改 (Ch 6)
**Sacrificial Architecture** — 被有意识地视为可丢弃的架构；不应过度投入 (Ch 6)
**Scientist Framework** — GitHub 的工具：让新代码与旧代码并行运行并比较结果；对外始终返回旧行为 (Ch 3)
**Service Template** — 预构建的 microservices 框架，内含 monitoring、logging、auth 等 plumbing (Ch 4)
**Share Nothing Architecture** — services 之间不存在会相互牵连的 coupling 点 (Ch 4)
**Snowflake Server** — 依赖人工定制和手工维护的 server (Ch 6)
**Systemwide Fitness Function** — 由多个独立 fitness functions 组成的集合，用于形成统一视角并支持 tradeoff 分析 (Ch 2)
**Two-Phase Commit** — 一种 transaction coupling，会像强核力一样把 components 紧紧绑在一起 (Ch 5)
**Vendor King** — 一种 antipattern：整个架构完全围绕某个 vendor product 构建 (Ch 7)
