# Glossary — Building Evolutionary Architectures (2nd Edition)

**Adaptation** — 通过并行保留 legacy behavior 应对变化，容易累积 technical debt；evolution 则在 FF 保护下原地改变并移除旧行为 (Ch 1, 9)
**Afferent Coupling (Ca)** — 入向依赖数：被多少组件依赖。高 Ca = 稳定 (Ch 4)
**Architectural Dimension** — 演化过程中必须被保留的架构视角：technical、data、security、operational (Ch 1)
**Architectural Fitness Function** — 对某些架构特征进行客观完整性评估的机制 (Ch 2)
**Architectural Quantum** — 可独立部署 + 高功能内聚 + 高静态耦合 + 同步动态耦合的最小组件单元，包含所有依赖 (Ch 5)
**Atomic Fitness Function** — 在单一上下文中运行，只检验架构的一个方面 (Ch 2)
**Auto-Disintegration** — 自动检测和清理不再使用的 service/resource (Ch 3)
**Bit Rot** — 当开发者绕过架构时，架构特征逐步被侵蚀 (Ch 1)
**Bounded Context** — DDD 概念：某领域相关一切在内部可见，对其他 context 不透明 (Ch 5)
**Business Capability** — 以领域为中心的组织单元；团队应围绕它组织 (Ch 9)
**Chaos Engineering** — 通过故障注入验证 resilience FFs。Netflix Simian Army 是典型实现 (Ch 4)
**Cognitive Load** — 团队处理系统与工作所需的有限认知容量；超载是缩小边界或提供 platform 支持的信号 (Ch 9)
**Component** — modules 的物理打包形式 (Ch 5)
**Connascence** — 比 coupling 更精确的度量体系，分 static 和 dynamic 两类 (Ch 5)
**Consumer-Driven Contracts** — consumer 为自己需要的 provider 行为编写测试 (Ch 3)
**Continuous Deployment** — pipeline 成功后自动部署到 production (Ch 3)
**Contract Spectrum** — 服务间契约在 strict 与 loose 之间的设计空间，不同协议和 payload styles 具有不同 coupling trade-offs (Ch 5)
**Cycle Time** — 工作单元从启动到完成的耗时；与演化速度成反比 (Ch 3, 8)
**Data Mesh** — 去中心化数据架构：domain ownership、data as product、self-serve platform、federated governance (Ch 5)
**Data Product Quantum (DPQ)** — 数据产品的量子单元：source-aligned、aggregate、fit-for-purpose (Ch 5)
**Deployment Pipeline** — 验证系统生产就绪性的多阶段构建机制 (Ch 3)
**Distance from Main Sequence** — `D = |A + I - 1|`，衡量模块设计平衡性 (Ch 4)
**Dynamic Equilibrium** — 软件开发生态中不断变化的平衡状态 (Ch 1)
**Efferent Coupling (Ce)** — 出向依赖数：依赖多少组件。高 Ce = 不稳定 (Ch 4)
**Expand/Contract Pattern** — 数据库重构模式：Expand→维护双套→等迁移→Contract (Ch 6)
**Feature Toggles** — 在 production 中隐藏新功能的可配置开关 (Ch 3)
**Fidelity Fitness Function** — 用 Scientist framework 验证重构行为一致性的 FF (Ch 4)
**Frozen Caveman Antipattern** — 过去事故催生的规则失去原始上下文后固化，形成非理性风险规避 (Ch 4)
**Herding Governance** — 随代码库改善逐步收紧 FF 阈值，从 warning 演进到 error (Ch 4)
**Holistic Fitness Function** — 在共享上下文中同时检验多个架构方面 (Ch 2)
**Hypothesis-Driven Development** — 将功能变更表述为 hypothesis，通过实验验证 (Ch 9)
**Immutable Infrastructure** — 系统完全以程序方式定义；bootstrap 后不允许手工变更 (Ch 7)
**Incremental Change** — 团队以小步方式构建和部署软件 (Ch 1, 3)
**Instability** — `I = Ce / (Ca + Ce)`，I=0 完全稳定，I=1 完全不稳定 (Ch 4)
**Inverse Conway Maneuver** — 按目标架构来设计团队结构 (Ch 1, 9)
**Last 10% Trap** — 工具快速解决前 80%，接下来 10% 极难，最后 10% 几乎无法完成。2nd ed 含 low-code/no-code 变体 (Ch 8)
**Module** — 相关代码的逻辑分组 (Ch 5)
**Parallel Change** — 安全实施向后不兼容接口变更的通用模式 (Ch 6)
**PenultimateWidgets** — 书中贯穿使用的示例公司 (Ch 1)
**Postel's Law** — 只发送必要数据，consumer 只依赖所需 fields；非 breaking change 不 version (Ch 7)
**Primordial Abstraction Ooze** — 底层失效的 abstraction 渗透各层引发混乱 (Ch 8)
**Refactoring** — 在不改变外部行为的前提下重组代码 (Ch 7)
**Restructuring** — 同时对结构与行为进行实质性修改 (Ch 7)
**Sacrificial Architecture** — 被有意识地视为可丢弃的架构 (Ch 7)
**Scientist Framework** — GitHub 工具：新代码与旧代码并行运行并比较结果 (Ch 4)
**Service Mesh** — 管理所有 sidecar proxy 的基础设施层 (Ch 5)
**Service Template** — 预构建 microservices 框架，内含 plumbing (Ch 5)
**Share Nothing Architecture** — services 间不存在相互牵连的 coupling 点 (Ch 5)
**Sidecar Pattern** — 把 operational concerns 放到 sidecar proxy 中，与业务代码正交解耦 (Ch 5)
**Snowflake Server** — 依赖人工定制和手工维护的 server (Ch 7)
**Stamp Coupling** — 传递包含多余字段的数据结构，制造隐性契约 (Ch 5)
**Systemwide Fitness Function** — 多个独立 FFs 组成的统一视角，支持 tradeoff 分析 (Ch 2)
**Team Topologies** — 四种团队类型：stream-aligned、enabling、complicated-subsystem、platform (Ch 9)
**Temporal Fitness Function** — 基于时间的 FF，检查 library staleness、break-upon-upgrade 等 (Ch 2)
**Two-Phase Commit** — transaction coupling，像强核力绑定 components (Ch 6)
**Vendor King** — antipattern：整个架构完全围绕某个 vendor product 构建 (Ch 8)
**Zone of Pain** — A-I 图上低 abstractness、低 instability 区域：大量 concrete implementation 处于 rigid dependency position (Ch 4)
**Zone of Uselessness** — A-I 图上高 abstractness、高 instability 区域：抽象缺乏 dependents (Ch 4)
