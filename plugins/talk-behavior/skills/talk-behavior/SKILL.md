# Talk Behavior：讲功能、行为、使用场景

## 谈什么

「行为」包含三层，都是要谈的：

| 层            | 回答的问题                       | 信号词                       |
| ------------- | -------------------------------- | ---------------------------- |
| 行为/使用场景 | 用户能感知什么？什么时候用？     | 你会得到、适合、什么时候用它 |
| 流程          | 几步？什么顺序？什么进什么出？   | 先…再…、分几轮、输入输出     |
| 机制          | 什么组件？什么思路？数据怎么流？ | 架构、调度、缓存、遍历方式   |

要排除的只有一层：**实现**——哪个文件、哪个函数、什么字段、什么常量、哪个版本号。

## 默认推导

用户未指定时，从提问方式判断：

- 「是什么 / 有什么用 / 怎么用 / 区别在哪 / 怎么工作」→ 按上面三层谈
- 「怎么实现 / 源码在哪 / 为什么报错」→ 可以进实现层

显式指令永远优先于推导。

## 怎么把实现层事实说成行为层

手里的事实常带着实现细节，读者要的是它干什么。做法：把名字换成它做的事，把数值换成它管的范围，把字段换成它承载的信息。

- 「最多保留 128 个候选」→「先撒网，只留最前面一百多个候选」
- 「低于阈值的直接淘汰」→「分数不够的进不了下一轮」
- 「每轮只给模型看当前阶段的材料」→「一轮一轮来，每轮只看该看的东西」

说正常话，不自造词，不装。表达方式照 no-bs 的「说人话」一节。

## 何时可以谈实现

命中任一条件即可：

- 用户点名追问实现细节
- 任务是定位 bug 或读报错
- 要说明的差异本身在实现层
- 用户给了代码、日志或配置让分析

## 输出前自检

扫一遍草稿：出现文件路径、函数名、常量名、配置字段名，且未命中上面的条件——改写或删除。
