# GitHub 仓库情报研究

给定一个或一组 GitHub 仓库，产出带证据分级的情报简报。单个仓库出完整档案，多个仓库加横向对比。只回答证据能支撑的强度，不越界。

## 核心原则（先于一切步骤）

1. **结论强度匹配证据层级**。筛查不是判决；「未发现异常」不等于「star 是真的」；实测强于 README 声明强于自评论文。
2. **仓库与工具用全名**。不造缩写，不造新术语——领域已有名字就用既有名。
3. **引用 issue 必核当前状态**：open、closed、已标修复版本、复现失败后关闭——状态随引用写出。复现失败后关闭的 issue 不得当作现存问题。
4. **「已核实」只能在读完正文后说**。搜索摘要、目录页、README 前几行，都不算核实。

## 五步流程

### 第一步：身份与机制

- 实读目标仓库 README 正文，取能力边界与核心架构。能力取 README 的措辞，不替作者总结拔高。
- 同名撞车排查：凡引用 registry（npm / PyPI）包数据，先核该包的 repository 字段与目标仓库归属一致。不一致即撞包，弃用其数据。

### 第二步：硬指标快照

- gh CLI 优先（已登录、配额高）；无 gh 再降级 curl + token。动手前查实际剩余配额，分页任务逐页存 checkpoint，剩额不足即停并报告进度。
- GraphQL 查：stars、pushedAt、watchers、issues（open 与 closed 分开）、discussions。单点快照，标注日期。
- 数字只陈述，不解读。解读留给第五步和选型段。

### 第三步：社区口碑

- **执行时发现来源，不预设清单**。先搜索盘点该仓库的讨论实际集中在哪些平台，哪有讨论去哪，没有的不要硬凑。
- 正负清单分开收。每条带：观点 + 完整 URL + 日期 + 来源类型。
- 排除官方自述：README、官网、厂商博客不算口碑；作者本人的帖与独立用户评价分列，不混排。
- **必须跑反方查询**：对要写下的正面结论，搜它的具体否命题（如「X 比 Y 慢的实测」），query 与命中记进报告。搜不到反证写「未发现反证」，不因此加分。
- 多仓库时按对象拆并行调研子任务，每对象交付压缩简报，不倒原文。

### 第四步：证据分级核验

每条关键结论标一档：

| 标记              | 条件                                        |
| ----------------- | ------------------------------------------- |
| `[verified]`      | 3+ 独立来源且含高可信源；必须能给出完整 URL |
| `[likely]`        | 2 来源未达上一档                            |
| `[single-source]` | 仅 1 来源                                   |
| `[conflicting]`   | 来源实质矛盾，列各方不强行消解              |
| `[unknown]`       | 未找到证据                                  |

三种证据形态分开写：实测 / 文档声明 / 推断。自评论文（作者测自己的系统）不算独立验证。同一内容多处转载按 1 个来源计。

### 第五步：star 真实性与活动

轻量筛查，四个动作：

1. 用 GitHub 官方周级 star 序列端点 `/repos/{owner}/{repo}/stargazers/history` 拉增长曲线。端点形状、分页、权限均执行时现场验证，不依赖记忆。
2. 算：峰值周增量、突发比（峰值周 ÷ 中位周）、前三周占比。
3. 事件对照：峰值周与已知公开事件（大 V 推文、Trending、发布会）比对。吻合 → 信号降级；不吻合 → 不下结论，记「已查来源未找到解释」。
4. registry 下载量做参考信号（周下载量 / star 比率），只作辅助——下载含 CI、镜像、重复安装，不是独立用户数。

输出三档，措辞就这三句，不扩展：

- **基准**：无异常信号
- **观察**：弱信号或小基数影响，不动作
- **升级取证**：时序异常，且已查来源无事件解释

逐 star 账号取证受 GitHub 端点权限约束；无权限时写「本轮不可得」，不绕、不用别的数据冒充。

## 反模式清单

- 不合成单一标量指标。watchers、issues、discussions 含义不同，等权相加无辩护基础。
- 不把筛查写成真伪判决。「掺水」「star 是假的」这类结论超出筛查证据，禁写。
- 不引用未核状态的 issue。
- 不把下载量叫真实采用。
- 不预设口碑来源。
- 不把一次性会话事实（失效日期、限速数字、撞包实例）写进结论——现场验证，现场记录在报告里。
- 不假设装有其他 skill。本 skill 自包含。

## 输出契约

每仓库六节，缺一不可：

1. **身份与机制**——它是什么、核心架构、能力边界。成段，不一句话打发。
2. **硬指标表**——stars / watchers / issues / discussions / 最近 push，标快照日期。
3. **口碑正面清单**——观点 + URL + 日期 + 来源类型。
4. **口碑负面清单**——同格式；issue 类附当前状态。
5. **star 真实性档位**——基准/观察/升级取证 + 依据 + 不可得信号标注。
6. **选型含义**——值不值得用、适用场景、已知风险。

多仓库时加横向对比表 + 全局边界声明：哪些验证过、哪些是推断、哪些 unknown。

报告开头放图例（五个分级标记各一句白话）；结尾放验证边界（一手直读 / 文档声明 / 推断各占多少）与判停依据。

## 升级取证路径

「升级取证」档位出现时才考虑，且先向用户报成本：

- 逐 star 账号质量分析——需管理员权限或历史事件数据，可能不可得或有实际费用
- 深挖传播事件——峰值周前后的全平台历史检索、目录站收录时间
- 放弃并标注——诚实写「本轮无法判定」优于硬凑结论
