# Help Me Read

把一个或多个 URL 转成高信息密度的助读稿。不套固定栏目模板，不输出多余元数据；顺着文章本身的体裁把核心判断、论证脉络、关键数据与案例、以及证据边界直接讲透，并在用户需要时展开逐段原文、译文与阅读提示。

## 1. 获取全文与事实边界

- **先抓完整内容再动笔**：按用户给出的顺序处理全部 URL。遇到 Substack 邮件跳转（`substack.com/app-link/...`）或短链时，先跟随重定向拿到真实文章 URL 再读取。正文中包含侧边栏（`<aside>`）、脚注、图表说明或高价值技术评论时，一并纳入阅读范围。
- **付费墙与截断边界**：若页面被付费墙、登录墙或反爬机制截断，只解读截断位置之前实际可见的正文，并明确标出截断位置与原因。严禁根据标题、副标题或前文预告去猜测和补写墙后未见的结论、方向或举例。
- **数字、单位与组件核对**：转述文中的数字、倍数、比例、单位口径（例如 GPU die 与完整芯片、在招岗位数与实际录用数）以及页面嵌入组件数量时，与原文逐项核对一致，不颠倒口径。
- **多来源独立呈现**：多个 URL 时，按顺序分别讲清每篇内容；需要横向比较时，在单篇内容之后追加跨来源对照。

## 2. 默认模式：顺着文章体裁直接讲透

用户只说 `help me read <url>`（未指定“逐段原文”或特定格式）时，直接输出与文章体裁匹配的完整助读稿，不打印 `## 来源 1`、`**输出语言：**` 等固定外壳，也不把短文或中等长度文章拆成“先看三行导览再停下问要不要继续”的两轮流程：

1. **开篇点明出处与主旨**：用一两句话交代作者、发布时间、文章主题，以及作者最核心的结论。若有付费墙截断或交互组件无法直接渲染，在此处一句话说明。
2. **顺着文章自身结构展开脉络与细节**：
   - **观点/评论类文章**：讲清作者反对什么、立论的几条核心理由、关键金句或原话，以及最终建议。
   - **数据报告/行业调研**：用表格和分点把数据源口径、每条核心 takeaway 的具体数字、涨跌幅度与背后的驱动因素完整列出来。
   - **工程复盘/技术架构文**：讲清旧方案痛点、新方案设计、实施步骤、踩坑与回归问题、最终性能/成本对比表，以及工程经验。
   - **调查报道/长篇叙事**：按事件与证据链递进梳理人物、公司、资金/技术流向与关键转折。
3. **区分事实、单方估算与作者立场**：文中有多方信源、做空报告、厂商营销数据或强烈情绪宣泄时，直接点明哪些是一方实测或官方文件、哪些是单方估算、哪些是作者主观推断。
4. **按需自然收尾**：短文和常规长文一轮直接讲完；只有面对超长万字文、或用户可能需要深挖文中引用的外部原始链接与某段原文时，才在末尾自然提一句可继续展开的方向。

## 3. 逐段精读模式：原文、译文与阅读提示

当用户明确要求“逐段读”、“展开原文”、“对照翻译”或针对某几节深读原文时，按原文顺序输出段落或段落组：

- **粒度与合并**：默认以自然段为单元；相邻短段讲同一个定义、论点或例子时，可合并为段落组并标明范围（如 `#### 段落组：第 3-5 段`）。保留所覆盖段落的全部原文细节与换行，不跨章节合并，不重排原文顺序。
- **呈现顺序**：每组依次给出 **原文** → **译文**（仅当原文语言不同于当前交流语言时提供） → **阅读提示**。
- **翻译标准（达、信、雅）**：
  - **达**：句子自然顺畅，符合中文（或目标语言）阅读习惯，一遍读懂。
  - **信**：保留原文限定词、语气、逻辑关系与不确定性，不暗中加强或削弱作者立场。
  - **雅**：贴合原文文体，干净利落，不带生硬机翻腔。术语解释、背景与双关留在阅读提示里，不塞进译文正文。
- **阅读提示（1-3 句）**：直接点出该段在全文中的作用、隐含前提、关键转折或术语含义；篇幅明显短于原文与译文，不用“此外”、“值得注意的是”等空话开头。
