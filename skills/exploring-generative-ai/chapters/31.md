# 第 31 章：TDD inside the agent loop - theater or actual value?

- **作者**：Birgitta Böckeler
- **日期**：2026-08-10
- **来源**：https://martinfowler.com/articles/exploring-gen-ai/tdd-in-the-agent-loop.html

## 核心思想

一个小型探索性 eval 发现，agent 在自己的 loop 内完整遵循 TDD 时，质量没有明显可辨的差异——非 TDD 方案甚至不止一次被排得更高，mutation score 也没有有意义的差异——而 TDD 运行的 token 成本至少是 3 倍。样本小；当作假设，不是定论。

## 实验设置

- 小/中/大型绿地业务逻辑任务；方案由 Sonnet 4.6 生成；由 Opus 4.8 盲评排名；TDD 遵循度由独立 agent 从会话 transcript 判断。
- 5 批；其中一批加了「test-first 但不完整 TDD」的变体。没有一次运行完美遵循 TDD；所有任务都是小型绿地逻辑。

## 结果与假设

- 在小型与中型任务中，非 TDD 方案排第 1、第 2；只有一次 TDD 运行排到第一（用的是加强过的 refactor-and-design-review prompt——而它的孪生运行排最后）。
- 假设：非 TDD 与 test-first 运行在编码前做了**完整的前置设计**（架构、数据类型、边界情况）；TDD 指令恰恰与它对着干——设计从局部最小决策中涌现，并被锁在第一个测试的形状上。没人写测试的行为压根没被实现。
- Ivett Ördög 的理论：训练数据包含完整函数及其描述，而不是一步步的 TDD 过程——所以模型的内部表示把需求直接映射到代码，而不是映射到抵达代码的过程。

## TDD 的目标——在 agent loop 内仍然成立吗？

| TDD 目标 | 在 agent loop 内的判定 |
|---|---|
| 测试先行 → 避免同义反复的测试 | 不可靠；一些 agent 仍拿输出对照实现本身检查 |
| 测试先行 → 可测试性 | 没有明确信号 |
| 红绿 → 证明测试有效 | 被削弱：红测试只有有人检查它**为什么**红才算数；agent 会跳过或假装红这一步。改用 mutation testing 监控回归有效性 |
| 测试先行 + 重构 → 驱动设计 | 未得到证明；非 TDD 设计更常得分更高 |
| 小步 → YAGNI | 以人为中心的收益：逼你思考的摩擦不会迁移到一个拿着完整需求的 agent 上；尽管有最小实现指令，agent 仍过度设计 |
| 小步 → 快速局部反馈 | Agent 不需要刻意小步也能相当好地调试红测试 |
| 小步 → 信心 / 管理恐惧 | Kent Beck 的理由是关于管理**人**的恐惧；当 agent 独自做 TDD 时，它不迁移 |

## 成本

- **至少 3 倍的 token**（更多轮次与工具调用；很多是 cache hit，所以美元涨幅小于 token）。
- **Prompt 维护**：TDD 与训练数据的取向相悖；prompt 需要反复加强，而且这类复杂指令集很可能随模型与版本漂移。

## 结论与替代方案

对模型应该**怎么**工作规定得过于具体不可持续；转而投资于监控结果并给出反馈——尽可能自动化——并仔细决定人在哪里仍是正确性的仲裁者。作者停止指示 agent 做 TDD，改用其他手段追求 TDD 的收益：

- **回归测试**：用 mutation testing 监控与改进有效性，而不是繁琐的 TDD 指令。
- **定期重构**：静态分析接入、结构/模块性 review、团队仪式，以及 files-touched 与单次变更 token 这类趋势。
- **信心**：例如 Approved Scenarios 方法——一个专用 runner，「冻结」人确认过的期望，违反时要求重新批准。

## 要点

1. 不要假设人的流程能迁移到 agent loop——测试它的机制在没有人在步骤里时是否仍然运作。
2. 与其用详细 how-to prompt 规定流程，不如用 sensors 监控结果。
3. 检查回归测试有效性的是 mutation testing，而不是红绿仪式。
4. 流程繁重的指令会成倍放大 token 成本与 prompt 维护负担。
