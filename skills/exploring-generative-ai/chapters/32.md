## 核心思想

一份关于可维护性 sensors 的实战报告：在通往生产的路径上实际跑了什么、哪些信号有用、computational sensor 在哪里触顶、需要 inferential 伙伴。实验刻意几乎不用 guides，以隔离 sensor 反馈的效果。

## 通往生产的路径上的 Sensor 部署

- **编码会话期间**（agent 旁边的快速反馈）：type checker、ESLint、Semgrep/SAST、dependency-cruiser、测试套件 + coverage、增量 mutation testing、pre-commit 里的 GitLeaks——全是 computational。
- **集成后（pipeline）**：同样的 computational sensors 在集成后在干净基础设施上重跑。
- **周期性（慢节奏 drift 检测）**：安全 review prompt、数据处理 review prompt（inferential）；依赖新鲜度报告、模块性/耦合 review（computational + inferential）。

## 静态代码分析：基础 Linting

- 最低垂的 AI 失败模式——最大函数参数、文件长度、函数长度、圈复杂度——**不在 ESLint 默认预设里**；必须手动配置。针对 agent 失败模式的社区规则集正在出现。
- **Self-correction guidance（自我修正引导）**：自定义 ESLint formatter 在消息里补充指令（例如 `no-explicit-any` 何时可以压制、怎么压制；阈值可以略微上调而不是永久压制）。证据表明有效：唯一缺这种引导的规则（圈复杂度），恰恰是 agent 不断通过上调阈值来消解的那条。
- 管理警告变得可行了：agent 能做判断，并让压制可见、可 review——静态分析一直想要的「干净房子」的机会。
- 风险：卫生指标带来的虚假安全感；**反馈过载**会把 agent 送进过度工程重构的漩涡；规则权衡（max-lines 与 max-lines-per-function 把复杂度挤进 prop chains）。

## 依赖规则与耦合数据

- **dependency-cruiser 规则**强制分层模块结构，错误消息扩展成重述分层概念的 self-correction guidance。Agent 违反规则几次后自我修正了——这是**替代在 markdown guide 里描述结构的有效做法**。局限：只能表达 import、文件名、文件夹能表达的东西。需要额外规则抓结构之外的新文件夹。
- **耦合指标**（基于 TypeScript compiler 的自定义 CLI）：可视化没有降低人的认知负担；LLM 对原始耦合数据的解读平淡——它把故意的 DI factory 和刻意的共享 schema 都标成了问题。合法模式需要压制机制，否则就成噪音。
- 耦合数据的实用用途：**review 的风险分诊**——知道变更文件有 10+ 调用者能聚焦人的注意力；AI review agent 能据此分配 token。

## AI 模块性审查

完全走 inferential、用强力模块性 prompts，结果**非常丰硕**：它发现了重复的路由代码、后端调用中的语义重复、穿过 40+ 文件的核心参数，以及放错位置在 wiring factory 里的认证逻辑。它也正确地**豁免**了原始耦合数据标为高耦合的枢纽。第二次独立运行暴露了第一次漏掉的问题——重要时，LLM 分析要多跑几遍。结论：设计与模块性问题上，只有 computational sensors 不够；inferential sensors 必须补上语义解读与取舍判断。没有人工 review **和**这些 AI review，agent 会累积无意的技术债。

## 作为 Regression Sensor 的测试套件

- 一个失败的在先测试逼出正确的问题：「是我破坏了什么，还是 spec 变了？」好套件降低 agent 破坏期望行为的概率——尽管它仍可能答错这个问题。
- **Coverage 不等于有效性**：一个 100% 语句覆盖的文件（靠一个大 acceptance test）没有单元测试，在 Stryker 下有 13 个存活 mutant。Acceptance 重型的套件在没有断言的情况下虚高覆盖——一种 **mutation testing** 能揭穿的虚假安全感。
- 工具箱：coverage（$）、property-based testing（$）、fuzz testing（$$）、mutation testing（$$）。
- 实践：给 agent 脚本去查询巨大的工具输出（如 Stryker 的 JSON），而不是把 context 塞满——「AI 帮我帮助 AI」。

## 工具：Sensor Sidecar

- 一个 vibe-coded CLI 按配置文件运行所有 computational sensors，持续或按间隔——像 test watch mode——给人一个抬头显示，给 agent 一份省 token、带引导增强的摘要（趋势 vs 快照、「越高/越低越好」、目标阈值、全局引导 prompt）。
- **让 agent 真的去检查 sensors 是难点**：AGENTS.md/skills 里的 guide 最容易但不可靠；hooks、git pre-commit hooks、或自定义 harness extension 是逐步更强的选项。
- 加一个 sensor 意味着写一个结果解析器；迁移到固定 JSON schema 之上的默认解析器，把定制推给用户——用户能 vibe-code adapter 时，插件系统不那么显然必要。
- 快速构建工具重要：慢工具链上的 sensor 套件会同时拖累人与 agent 的 feedback loop；「可沙箱化」是 harness 工具的首要关注点。
- **有效性**：记录 sensor 状态历史来回答「这个 harness 在起作用吗？」——sensors 随时间失败变少，说明 guides/models 在改进；从不失败的 sensors 可能没必要；频繁失败的显示 guides 哪里需要补。

## 要点

1. Computational sensors 在文件/函数级别表现出色；跨文件设计问题需要带强力 prompts 的 inferential sensors。
2. 给每个 sensor 信号加上 self-correction guidance——差异在 agent 行为上可测量。
3. 测试写作一委托给 AI，mutation testing 就变得关键。
4. 警惕 sensor 冲突与反馈过载；信号多并不自动更好。
5. Sensors 提升信任、改善 review，但它们不会把人移出 loop。
