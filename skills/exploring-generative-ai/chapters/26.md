# 第 26 章：Harness engineering for coding agent users

- **作者**：Birgitta Böckeler
- **日期**：2026-04-02
- **来源**：https://martinfowler.com/articles/harness-engineering.html
- **备注**：取代 2026-02-17 的 memo《Harness Engineering - first thoughts》；memo 的 URL 现已重定向到本文。

## 核心思想

Agent = Model + Harness。外层 harness——我们围绕模型为用例构建的一切——服务于两个目标：提高 agent 第一次就做对的概率，以及在问题到达人眼之前提供自我修正的 feedback loop。好的 harness 把人的输入导向最重要的地方；它不试图消除人的输入。

## Guides 与 Sensors

Harness 组合两种控制方向：

- **Guides（feedforward controls，前馈控制）**——预判 agent 的行为，在它行动**之前**引导；提高第一次尝试就做对的概率。
- **Sensors（feedback controls，反馈控制）**——在 agent 行动**之后**观察，帮它自我修正。当信号针对 LLM 消费优化时威力最大，例如包含自我修正指令的 linter 消息——一种「正向 prompt injection」。

只用一个方向的失败模式：

- **只有 feedback** → agent 反复犯同样的错。
- **只有 feedforward** → agent 编码了规则，却从不知道它们是否有效。

## Computational vs Inferential

每个 guide 或 sensor 有两种执行类型之一：

- **Computational（计算式）**——确定性、快速，由 CPU 执行：测试、linter、type checker、结构化分析。毫秒到秒级；结果可靠。便宜到每次变更都能跑。
- **Inferential（推断式）**——语义分析、AI code review、「LLM 当裁判」；通常走 GPU/NPU。更慢、更贵、非确定性——但提供丰富的指导与语义判断。模型强、任务合适时，inferential sensor 能特别提升信任。

Fowler 的示例矩阵：

| 关注点 | 方向 | 类型 | 示例 |
|---|---|---|---|
| 编码约定 | feedforward | inferential | AGENTS.md、skills |
| 项目引导说明 | feedforward | 两者 | skill + bootstrap script |
| 代码改造 | feedforward | computational | OpenRewrite recipe tooling |
| 结构测试 | feedback | computational | pre-commit hook 跑 ArchUnit 模块边界测试 |
| Review 指令 | feedback | inferential | skills |

## Steering Loop

人的工作是** steer **agent：通过迭代 harness——每当一个问题发生多次，就改进 guides 和 sensors，让它在未来更不可能发生（或不可能发生）。Agent 让构建自定义控制更便宜：结构测试、从观察到的模式起草规则、自定义 linter、从 codebase 考古中提炼 how-to 指南。

## 时机：Keep Quality Left（质量左移）

按成本、速度与关键性把 sensors 分布到生命周期各阶段——问题发现得越早，修复越便宜：

- **提交/集成前**——linter、快速测试套件、基础 code-review agent。
- **集成后 pipeline**——mutation testing、能看到更大图景的更广 review。
- **持续 drift 与 health sensors**——变更生命周期之外：死代码检测、测试覆盖质量、依赖扫描器、恶化的 SLO、抽样响应质量的 AI 裁判。

## Regulation Categories（调节类别）

Harness 像一个 **cybernetic governor（控制论调节器）**，把 codebase 调节到期望状态。值得调节的三个类别：

- **Maintainability harness（可维护性 harness）**——内部代码质量；最容易的一类，现成工具最多。Computational sensor 可靠抓住结构问题（重复、复杂度、覆盖、架构漂移、风格）。Inferential sensor 部分抓住语义问题（语义重复、冗余测试、过度工程）——贵且概率性。两者都不能可靠抓住误诊、多余功能或误解的指令；如果人从未说明他们要什么，正确性在任何 sensor 的职责之外。
- **Architecture fitness harness（架构适配 harness）**——fitness function：feedforward 性能或可观测性要求的 guides，feed back agent 是改进还是劣化了它们的 sensors。
- **Behaviour harness（行为 harness）**——房间里的大象：引导与感知功能行为。当前实践（功能 spec 作 feedforward + AI 生成的全绿测试套件作 feedback）对 AI 生成的测试信任过度；approved-fixtures 模式能选择性帮忙，但不是全面答案。

## Harnessability（可驾驭性）

不是每个 codebase 都同样适合 harness。强类型带来 type-checking sensor；清晰的模块边界带来架构约束规则；抽象掉细节的框架隐式提高 agent 的成功率。绿地团队可以从第一天就内建 harnessability；遗留团队面对最难的问题——harness 在最需要的地方最难建。

## Harness Templates（驾驭模板）

常见服务拓扑可能演化出 harness templates：把 agent 拴到某拓扑的结构、约定与技术栈上的 guides 和 sensors 包。团队可能部分按可用的 harness 选技术栈。预期会遇到与服务模板相同的版本与漂移问题——更糟，因为非确定性控制更难测试。

## 人的角色

人类开发者带来一种**隐式** harness：吸收的约定、对复杂度的认知痛苦、组织对齐、社会问责、创造思考空间的小步节奏。Coding agent 一样都没有。Harness 把经验带来的东西外化、显式化——但只能走这么远。目标不是消除人的输入，而是把它导向最重要的地方。

## 要点

1. 永远把 guides 与 sensors 配对；单独一个方向就有命名的失败模式。
2. 能上 computational 就优先；语义判断再补 inferential。
3. Steer harness，而不是 steer 每个输出：问题重复出现时，修控制。
4. Keep quality left：把 sensors 分布到会话、pipeline 与持续 drift 检测。
5. Harnessability 是 codebase 属性——选择技术、塑造技术时把可治理性放在心上。
