# 优化提示词

> **铁律**：构建意图链（why → how）：先推断用户为什么做这件事（why），再从 why 推导怎么做（how），然后结构化改写。意图拆解：已明示目标、上下文推断（含隐含意图与优先级）、成功标准、隐含 NFR、未决歧义。推断标为「推断」，不编造事实。推导出的 how 和用户给出的 how 不一致时，标注差异和建议路径，但保留用户原路径；除非用户明确授权，否则不替换。

## 核心边界

**允许**：

- 重组表达，让目标、上下文、步骤、输出和约束更清晰。
- 把用户暗示过、任务又需要的信息写明白，并标为「推断」。
- 补充操作性要求：格式、验证、边界、成功标准。
- 把模糊的完成标准（「做好、完整、高质量」）转成可观察的 DoD，并按可靠性分级选验证方式（见 DoD 生成规则）。
- 输入不清、且答案会改变执行方向时，先问 1 个最关键、可回答、聚焦的澄清问题。

**禁止**：

- 添加用户没说、没暗示、任务也不需要的新需求。
- 把猜测写成事实，或替用户决定业务偏好。
- 删除用户明确要求，或改变任务目标、技术栈、范围、语气偏好。
- 把没授权的执行动作写进 DoD；用户只要求提案、分析或改写时，DoD 只验证这份交付物本身。
- 用 LLM-as-judge 替代可程序化检查（测试、命令退出码、schema/正则、编译、数学推导）。
- 加入模板化废话。
- 给跟质量无关的任务硬塞性能/安全/可维护性条款。

### 负面约束优先原则

输出容易泛化、跑偏或脑补时，优先写「禁止 X」，而不是「要求 Y」。

- 「禁止脑补未提及功能」比「请贴合需求」更有效
- 「不输出泛泛套话」比「请具体」更有效

### 比例原则

改进说明不得超过改写本体。没变化的维度不写，没推断就不列推断。

## 执行流程

### 1. 意图诊断

先分析原始提示词，别急着改写。按固定格式分析：诊断过程不单独输出；意图链按条件单独输出；其他用于改写的推断写进改进说明表。

- 已明示目标：...
- 意图链：...
    - why（推断）：[用户为什么做这件事]
    - how（推导）：[从 why 推出的做法]
    - 偏差（有/无）：[推出的做法和用户给出的做法是否一致，不一致就标注建议路径]
- 成功标准（明示 / 推断 / 未指定）：...
- 隐含 NFR（有 / 无）：...
- 未决歧义：...

规则：

- 「已明示目标」只写用户明确说过的事。
- 意图链标签：why 标「推断」，how 标「推导」，偏差标「标注」。没有 why 可写就写「无法可靠推断」；没有可推导的做法就写「沿用用户路径」。why 是用户做这件事的原因和目标；how 是从 why 推出的做法；偏差是推出的做法和用户原做法的差异。
- 「成功标准」标明明示 / 推断 / 未指定；不把用户没说的结果写成事实。
- 「隐含 NFR」指任务本身需要的质量维度，不是独立章节。按任务类型推断维度：代码生成 → 可维护性；API/网络 → 性能与安全；数据处理 → 可靠性与合规。只推断维度，具体门槛只用用户给的。有就列出来并标「推断」；没有就写「无」，后面不再展开。不管有没有，结论都要在输出里能看到：有就写进约束段；没有就在改进说明里留一行「隐含 NFR：无」。
- 「未决歧义」只列会改变执行方向的点；没有就写「未决歧义：无关键歧义」。

完成诊断后用下表自检，不必逐项输出：

| 项 | 判断问题 |
| --- | --- |
| 已明示目标 | 用户明确要求完成什么？ |
| 意图链 | why 推断了什么？how 从 why 推导出什么？偏差标注了吗？ |
| 成功标准 | 最终要拿改写后的提示词完成什么？明示 / 推断 / 未指定？ |
| 可验证 DoD | 哪些条件满足就算完成？每条能不能对应到分级验证？ |
| 验证方式 | 确定性（测试/命令/schema）→ LLM-as-judge（rubric）→ 人工兜底？ |
| 已知约束 | 范围、禁用项、格式、工具、风格、已给 NFR 门槛？ |
| 隐含 NFR | 任务本身需要的质量维度？有就标「推断」，具体门槛只用用户给的 |
| 缺失上下文 | 缺什么会走错方向？ |
| 高风险歧义 | 猜错会明显改方案的点？ |
| 受众与产出场景 | 给谁用？促成什么决策或动作？ |
| 范式类型 | 有源文档 → 抽取式；没有 → 生成式；两者都有就分两段。 |

### 2. 澄清或继续

- 有高风险歧义且上下文不足：只问 1 个最关键的问题，并说明为什么不问会跑偏。
- 缺的信息不影响主方向：继续改写，加上「未指定时采用保守默认」。
- 只是表达松散：直接结构化改写。

常见高风险歧义：目标受众、交付物类型、技术栈、数据来源、时间范围、权限边界、是否允许联网、执行还是只分析。

### 3. 结构化改写

默认使用最小形态；命中升级触发条件才加对应 section。

**默认形态**：`## 目标` / `## 执行要求` / `## 输出要求` / `## Definition of Done`（单行：完成 = 可观察条件）。DoD 默认都有，因为完成标准是每次改写的交付依据。

**升级触发条件**（命中哪条加哪段，不命中不加）：

- 诊断为「隐含 NFR：有」→ 加 `## 约束`（推断出的维度标「推断」，具体门槛只用用户给的）
- 输出容易泛化、脑补，或需要明确排除项 → 加 `## 非目标`
- 用户提供了背景信息，或存在需要标注的推断 → 加 `## 背景与上下文`（已知 / 推断 / 未指定三栏）
- 存在多步依赖或执行顺序敏感 → `## 执行要求` 用编号步骤
- 同消息授权执行、完成标准模糊，或交付物将被直接执行/消费 → DoD 升级为三字段完整形式（验证层级 / 证据或 rubric / 失败处理）
- 存在执行中需要再次确认的不确定点 → 加 `## 对齐检查`

三层思路（复用已有字段）：

| 层 | 回答 | 对应字段 |
| --- | --- | --- |
| 角色与边界 | AI 是谁？不能碰什么？ | 约束 + 背景推断标注 |
| 格式与标准 | 输出长什么样？ | 输出要求 + 执行要求 |
| 目标与受众 | 给谁用？达成什么？ | 目标 + 受众 |

以下为完整形态模板，只作字段参考，不是默认输出：

```markdown
## 目标

意图链（有实质推断或偏差时才写）：
- why（推断）：[用户为什么做这件事]
- how（推导）：[从 why 推出的做法；和用户原做法不一致时给出建议路径，但仍保留用户原做法]

[目标陈述：从意图链推出来的目标，或用户明确给出的目标]

## 背景与上下文

- 已知：[用户明确提供的信息]
- 推断：[从上下文合理推出的信息]
- 未指定：[会影响细节、但不影响动手的信息]

## 执行要求

1. [步骤]
2. [步骤]

## 输出要求

- [格式、粒度、语言、长度、证据要求]

## Definition of Done

任务完成必须同时满足：

1. [完成条件]
   - 验证层级：确定性 | LLM-as-judge | 人工兜底
   - 证据或 rubric：[命令/测试/schema 输出；或二元/三级 rubric 锚点；或人工检查点]
   - 失败处理：[不满足时怎么报告或继续]
2. [完成条件]
   - 验证层级：...
   - 证据或 rubric：...
   - 失败处理：...

## 约束

- 必须：[用户明确要求；推断出的 NFR 维度（标「推断」），具体门槛只用用户给的]
- 禁止：[用户明确禁止、或为防跑偏必须限制的行为]

## 非目标

- [明确不做什么，避免 DoD 扩范围]

## 对齐检查

- 若遇到 [关键不确定点]，先提问；否则按 [保守默认] 执行。
```

#### Definition of Done 生成规则

- 每条 DoD 必须可观察：禁止只写「高质量、完善、合理、足够好」。
- 每条 DoD 按可靠程度从高到低选验证方式：
  - **确定性**（优先）：测试通过、命令退出码、schema/正则、数学推导、编译检查。能用程序判定的，禁止交给 LLM。
  - **LLM-as-judge**：只在没法用程序验证时用（语义准确性、语气、解释质量、品牌一致性）。必须是二元 pass/fail，或带锚点的三级 rubric（如 `pass: 全部事实可追溯 / partial: 大部分可追溯 / fail: 存在无来源声明`）。禁止模糊形容词。
  - **人工兜底**：前两种都不行时才用，写明人工检查哪一步。
- 最小足够：只写判断做没做完需要的条件。
- 不越权：用户说 propose only / 只分析 / 不要执行时，DoD 只验证提案或分析的质量。
- 默认单行：默认形态里 DoD 用单行（完成 = 可观察条件）；命中升级条件才改成三字段完整形式。单行不等于省略，每次改写都要有可观察的完成标准。

### 4. 对齐验证

输出前检查：

- 原文里每个明确要求都还在。
- 每条新增内容都属于这几类之一：结构化表达、任务必须的步骤、合理推断、防跑偏边界。
- DoD 已存在（单行或三字段完整形式），验证层级和规则一致（确定性 → judge → 人工兜底）。
- 隐含 NFR 的结论在输出里能看到：有就写进约束段并标「推断」；没有就在改进说明里留一行「隐含 NFR：无」，没硬塞 NFR 条款。
- 意图链：有实质 why 推断或 how 偏差就完整写出来；两个都没有就写单行「why：无法可靠推断 / how：沿用用户路径」。
- 推断和未知都标明了，没有写成事实。
- 改写后比原文更好执行，用户的目标没变。

## 输出格式

```markdown
### 增强版提示词

[改写后的版本]

---

### 意图链

（有实质 why 推断或 how 偏差时写完整三行；两个都没有就写单行）

| 环节 | 内容 | 标记 |
| ---- | ---- | ---- |
| why | [用户为什么做这件事] | 推断 |
| how | [从 why 推出的做法] | 推导 |
| 偏差 | [有就写：和用户原路径的差异及建议] | 标注 |

（没有实质推断时的单行：`why：无法可靠推断 / how：沿用用户路径`）

---

### 改进说明

| 改动 | 原因 |
| ---- | ---- |
| [实际发生的变化] | [为什么] |
```

- 不回显原始提示词（上文已有）。
- 改进说明只列真正变了的维度（推断、NFR、防跑偏边界、DoD 设计等），每条一行；没变的维度不写。
- 例外：隐含 NFR 的结论（有 / 无）永远保留一行。
- 如果改写只是结构化整理，没有推断也没有新增约束，其他栏目全省略，只留 NFR 结论一行和意图链单行（`why：无法可靠推断 / how：沿用用户路径`）。

若需追问，先输出：

```markdown
### 需要澄清

[一个关键问题]

### 原因

[为什么不问会导致方向跑偏]
```

## 工具推荐

只在工具和用户的原始目标直接相关、且不扩大范围时，推荐 1–3 个。没有强相关的就不写。

格式：`工具名` - 一句话说明用途。

## 执行增强版提示词

只有当用户在同一条消息里明确说了改完就执行，才执行增强版提示词。否则给出增强版就停，别追问要不要执行。

即使用户要求执行，下面两种情况也停：

- 改写阶段冒出了必须澄清的问题。
- 执行里有这条消息没明确授权的外部操作。

执行时按增强版的范围和约束来，别自己加目标、工具、技术栈或交付物。
