# 优化提示词

> **铁律**：构建意图链（why → how）：先推断用户为什么做这件事（why），再从 why 推导怎么做（how），然后结构化改写。意图理解：已明示目标、上下文推断（含隐含意图与优先级）、成功标准、隐含 NFR、未决歧义。推断标为「推断」，不编造事实。推导出的 how 和用户给出的 how 不一致时，写明差异和建议路径，但保留用户原路径；除非用户明确授权，否则不替换。

## 核心边界

**允许**：

- 重组表达，让目标、上下文、步骤、输出和约束更清晰。
- 把用户暗示过、任务又需要的信息写明白，并标为「推断」。可以推断：「帮我优化这个提示词」→「当前提示词效果不好」。不可以推断：「帮我优化这个提示词」→「用户想要代码生成相关的约束」。
- 补充操作性要求：格式、验证、边界、成功标准。
- 把模糊的完成标准（「做好、完整、高质量」）转成可观察的 DoD，并按可靠性分级选验证方式（见 DoD 生成规则）。
- 输入不清、且答案会改变执行方向时，先问 1 个最关键、可回答、聚焦的澄清问题。

**禁止**：

- 添加用户没说、没暗示、任务也不需要的新需求。
- 把猜测写成事实，或替用户决定业务偏好。
- 删除用户明确要求，或改变任务目标、技术栈、范围、语气偏好。
- 把没授权的执行动作写进 DoD；用户只要求提案、分析或改写时，DoD 只验证这份交付物本身。
- 用 LLM-as-judge 替代可程序化检查。
- 约束只写与任务直接相关的维度。

### 正面目标优先，禁令兜底

默认写正面目标。否定式会把被禁行为带进上下文，反而更容易出现。「禁止 X」只在无法正面表达的硬边界使用，并配上正面目标。

- 正面：「只输出用户要求的内容」；需要硬边界时补禁令：「禁止新增功能」
- 正面：「每句都有具体内容」；需要硬边界时补禁令：「不输出套话」

### 比例原则

改进说明不得超过改写本体。没变化的维度不写，没推断就不列推断。

## 执行流程

### 1. 意图诊断

按固定格式分析：诊断过程不单独输出；意图链按条件单独输出；其他用于改写的推断写进改进说明表。

- 已明示目标：...
- 意图链：按铁律格式输出（why 标「推断」，how 标「推导」，偏差标「偏差」；没有 why 就写「无法可靠推断」，没有可推导的做法就写「沿用用户路径」）。
- 成功标准（明示 / 推断 / 未指定）：...
- 隐含 NFR（有 / 无）：...
- 未决歧义：...

规则：

- 「已明示目标」只写用户明确说过的事。
- 「成功标准」标明明示 / 推断 / 未指定；不把用户没说的结果写成事实。
- 「隐含 NFR」指任务本身需要的质量维度，不是独立章节。按任务类型推断维度：代码生成 → 可维护性；API/网络 → 性能与安全；数据处理 → 可靠性与合规。只推断维度，具体门槛只用用户给的。有就列出来并标「推断」；没有就写「无」，后面不再展开。不管有没有，结论都要在输出里能看到：有就写进约束段；没有就在改进说明里留一行「隐含 NFR：无」。
- 「未决歧义」只列会改变执行方向的点；没有就写「未决歧义：无关键歧义」。

### 2. 澄清或继续

- 有高风险歧义且上下文不足：只问 1 个最关键的问题，并说明为什么不问会跑偏。
- 缺的信息不影响主方向：继续改写，加上「未指定时采用保守默认」。
- 只是表达松散：直接结构化改写。

常见高风险歧义：目标受众、交付物类型、技术栈、数据来源、时间范围、权限边界、是否允许联网、执行还是只分析。

### 3. 结构化改写

默认使用最小形态；命中升级触发条件才加对应 section。

**默认形态**：`## 目标` / `## 执行要求` / `## 输出要求` / `## Definition of Done`（单行：完成 = 可观察条件）。DoD 默认都有，因为完成标准是每次改写的交付依据。

**升级触发条件**（命中哪条加哪段，不命中不加）：

- 诊断为「隐含 NFR：有」→ 加 `## 约束`（推断出的维度标「推断」，具体门槛只用用户给的）
- 输出容易泛化、脑补，或需要明确排除项 → 加 `## 非目标`
- 用户提供了背景信息，或存在需要标注的推断 → 加 `## 背景与上下文`（已知 / 推断 / 未指定三栏）
- 存在多步依赖或执行顺序敏感 → `## 执行要求` 用编号步骤
- 同消息授权执行、完成标准模糊，或交付物将被直接执行/消费 → DoD 升级为三字段完整形式（验证层级 / 证据或评分标准 / 失败处理）
- 存在执行中需要再次确认的不确定点 → 加 `## 待确认`

三层思路（复用已有字段）：

| 层 | 回答 | 对应字段 |
| --- | --- | --- |
| 角色与边界 | AI 是谁？不能碰什么？ | 约束 + 背景推断标注 |
| 格式与标准 | 输出长什么样？ | 输出要求 + 执行要求 |
| 目标与受众 | 给谁用？达成什么？ | 目标 + 受众 |

完整形态模板见 `references/full-template.md`。

#### Definition of Done 生成规则

- 每条 DoD 必须可观察：禁止只写「高质量、完善、合理、足够好」，也禁止无判据的自我评价（「检查是否完整」「确认没问题」）。确定性条件指向产出证据（字段、计数、命令输出）；语义条件用带锚点的评分标准。
- 每条 DoD 按可靠程度从高到低选验证方式：
  - **确定性**（优先）：测试通过、命令退出码、schema/正则、数学推导、编译检查。能用程序判定的，禁止交给 LLM。
  - **LLM-as-judge**：只在没法用程序验证时用（语义准确性、语气、解释质量、品牌一致性）。必须是二元 pass/fail，或带锚点的三级评分标准（如 `pass: 全部事实可追溯 / partial: 大部分可追溯 / fail: 存在无来源声明`）。禁止模糊形容词。
  - **人工兜底**：前两种都不行时才用，写明人工检查哪一步。
- 可行性：每条 DoD 按「确定性、LLM-as-judge、人工兜底」的优先顺序选验证方式，且所选方式在任务实际可用的手段内。三者都不可行的，列入「待确认」或在改进说明标注「未验证」；不静默降低标准。
- 分工：指导过程的约束写执行要求，验收结果的检查写 DoD。每条 DoD 判定所需的标准必须能找到：写在 DoD 里，或在执行要求里有完整定义并被 DoD 明确点名引用；不复制原文。
- 最小足够：只写判断做没做完需要的条件。
- 不越权：用户说 propose only / 只分析 / 不要执行时，DoD 只验证提案或分析的质量。
- 默认单行：默认形态里 DoD 用单行（完成 = 可观察条件）；命中升级条件才改成三字段完整形式。单行不等于省略，每次改写都要有可观察的完成标准。

### 4. 交付前核对

输出前检查：

- 原文里每个明确要求都还在。
- 每条新增内容都属于这几类之一：结构化表达、任务必须的步骤、合理推断、防跑偏边界。
- DoD 已存在（单行或三字段完整形式），验证层级与 DoD 生成规则一致。
- 隐含 NFR 和意图链按各自规则输出，结论在输出里能看到。
- 推断和未知都标明了，没有写成事实。
- 用户的目标没变。

## 输出格式

```markdown
### 增强版提示词

[改写后的版本]

---

### 意图链

（有实质 why 推断或 how 偏差时写完整三行；两个都没有就写单行）

| 环节 | 内容 | 标记 |
| ---- | ---- | ---- |
| why | [用户为什么做这件事] | 推断 |
| how | [从 why 推出的做法] | 推导 |
| 偏差 | [有就写：和用户原路径的差异及建议] | 标注 |

（没有实质推断时的单行：`why：无法可靠推断 / how：沿用用户路径`）

---

### 改进说明

| 改动 | 原因 |
| ---- | ---- |
| [实际发生的变化] | [为什么] |
```

- 改进说明只列真正变了的维度（推断、NFR、防跑偏边界、DoD 设计等），每条一行；没变的维度不写。
- 例外：隐含 NFR 的结论（有 / 无）永远保留一行。
- 如果改写只是结构化整理，没有推断也没有新增约束，其他栏目全省略，只留 NFR 结论一行和意图链单行（`why：无法可靠推断 / how：沿用用户路径`）。

若需追问，先输出：

```markdown
### 需要澄清

[一个关键问题]

### 原因

[为什么不问会导致方向跑偏]
```

## 工具推荐

只在工具和用户的原始目标直接相关、且不扩大范围时，推荐 1–3 个。没有强相关的就不写。

格式：`工具名` - 一句话说明用途。

## 执行增强版提示词

只有当用户在同一条消息里明确说了改完就执行，才执行增强版提示词。否则给出增强版就停，别追问要不要执行。

即使用户要求执行，下面两种情况也停：

- 改写阶段冒出了必须澄清的问题。
- 执行里有这条消息没明确授权的外部操作。

执行时按增强版的范围和约束来，别自己加目标、工具、技术栈或交付物。
