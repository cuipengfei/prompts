# Talk Behavior：讲功能、行为、使用场景

## 讲到哪一层

根据用户的问题，选择需要讲的内容：

| 层次 | 回答什么 |
| --- | --- |
| 行为与使用场景 | 用户能得到什么，什么时候使用 |
| 流程 | 谁先做什么，收到什么，交给谁 |
| 机制 | 哪些组件参与，数据怎样流动，为什么这样工作 |

用户只问有什么用，就说明用途。问怎么工作，再讲相关流程和机制。需要引入新概念时，说明这个概念在解释哪个问题。

用户的明确要求优先。默认省略与问题无关的文件路径、函数名和配置字段。

## 把过程讲清楚

先说清楚当前讲的是哪个工具、方案或场景。同一个对象始终使用同一名称；有多个方案时，分别讲清各自的过程。

涉及多方时，按发生顺序说明：谁拿到什么，做了什么，交给谁，接收方接着做什么。数据保存在谁那里、状态何时改变，会影响用户理解时，一并交代。

流程中有条件时，把条件放在对应步骤旁边。只讲已知的过程；缺少哪一步的信息，就说明哪一步尚未确认。

## 保留有用的信息

保留区分对象所需的名称，以及会影响答案的数字、条件和限制。读者可能不熟悉的名称，在第一次出现时解释作用，后文继续沿用。

例如讲数量上限时，直接说「最多保留 128 个候选」。

省略与问题无关的字段写法时，仍要说清字段携带什么信息。用自然、准确的常用说法；有用的标准术语就保留，不自造词，也不用抽象词组把普通意思写复杂。

## 何时可以谈实现

以下情况可以说明相关的实现内容：

- 用户追问实现细节。
- 任务是定位 bug 或分析报错。
- 要说明的差异本身涉及实现。
- 用户提供代码、日志或配置，要求分析。

只展开回答当前问题所需的部分。准确的数量、版本或字段名称会影响判断时，保留这些信息。

## 输出前自检

- 用户问的用途、流程或机制，是否已经回答清楚？删除与问题无关的层次和背景。
- 涉及多方时，读者能否分清每一方拿到什么、做了什么、交给谁，以及必要的保存位置和状态变化？
- 名称、精确数字、条件和限制是否仍与依据一致？
- 文件路径、函数名和配置字段是否确实帮助回答当前问题？无关内容删除。
