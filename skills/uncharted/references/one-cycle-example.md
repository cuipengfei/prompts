# 一次完整循环：注册用户没有完成核心操作

这是一个虚构案例，用于展示各阶段怎样连接。案例中的 7 天阈值由产品团队确认，只对这个案例有效。

## 1. 实践问题

团队观察到一批用户完成注册和首次登录后，没有完成任何核心操作。现有描述是“onboarding 效果不好”。

输入：事件记录、用户访谈和当前产品定义。

需要保留的未知：不同账户类型是否采用相同时间范围。

## 2. 划分问题空间

候选维度：

- 注册是否完成；
- 首次登录是否完成；
- 核心操作是否完成；
- 从注册到核心操作经过多长时间。

通过检查：每个维度都能从事件记录观察，并且改变其中一项不会自动决定其他项目。

产物：四个可以分别检查的问题维度。

## 3. 命名元素

产品团队已经确认以下内部定义：

> dormant signup：已经完成注册和首次登录，并且 7 天内没有完成任何核心操作的用户。

包含范围：满足全部三个条件的正式用户。

排除范围：注册未满 7 天的用户、测试账户，以及采用其他 onboarding 规则的账户。

通过检查：团队可以把具体账户归入或排除该术语；该术语能够直接进入分析问题和执行规则。

来源状态：已核实，依据当前产品定义。该定义只适用于当前产品。

## 4. 形成模式

情境：用户完成注册和首次登录，随后停在核心操作之前。

问题：怎样提高核心操作完成率，同时避免 onboarding 步骤增加过多操作负担。

力量：

- 说明完整度：更多指导可以减少理解困难；
- 完成负担：更多步骤会增加退出机会。

候选响应：先显示完成首个核心操作所需的最少指导，在用户遇到阻碍时再显示补充说明。

后果：初始操作更短；部分用户可能较晚才看到完整说明。

边界：该响应只适用于问题来自指导数量或出现时机的案例。功能错误、权限问题和服务异常需要进入其他诊断流程。

来源状态：待核实。它需要产品数据和用户观察支持，不能因为听起来合理就进入正式规则。

## 5. 核实资料并声明框架

核实以下内容：

1. 产品文档怎样定义注册、首次登录和核心操作；
2. 事件系统怎样记录这些状态；
3. 7 天阈值由谁制定，适用于哪些账户；
4. 访谈和事件数据是否支持“指导负担”这个解释；
5. 是否存在其他合理解释，例如权限错误或功能故障。

本案例采用的知识框架：

- 权威来源：当前产品定义和事件 schema；
- 核心词汇：dormant signup、核心操作、说明完整度、完成负担；
- 有效证据：事件记录确认行为，用户访谈帮助解释原因；
- 未知：不同账户类型是否需要不同规则。

## 6. 编写规则候选

```text
IF 账户已完成注册和首次登录，注册已满 7 天，并且没有核心操作记录
THEN 将账户标记为 dormant signup，进入 onboarding 问题分析
UNLESS 账户是测试账户，或适用另一套已经确认的 onboarding 规则
```

人确认术语、阈值、事件字段和例外后，AI 才执行该规则。

## 7. 执行与边界案例

应触发：正式账户注册第 8 天，已经登录，没有核心操作记录。

接近触发但应跳过：正式账户注册第 6 天，已经登录，没有核心操作记录。

例外：测试账户注册第 10 天，没有核心操作记录。

## 8. 根据结果回溯

如果企业账户持续被错误标记，而企业账户采用另一套 onboarding 周期，返回“命名元素”，收紧 dormant signup 的适用范围。

如果规则执行正确，但团队发现核心操作并不能代表用户获得价值，返回“核实资料”和“知识框架”，重新确认核心操作的定义及有效性标准。

如果相同输入在规则和知识都未变化时仍得到不同判定，检查模型、工具和运行条件。
